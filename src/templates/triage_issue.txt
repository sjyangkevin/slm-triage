=== EVALUATION CRITERIA ===
For Issues, evaluate the content by looking at the following aspects. Be reasonable. Simple bugs or feature requests require less exhaustive detail than complex ones.
1. Description: A clear description of the issue, what happened, and what should happen instead. Very vague descriptions should be penalized.
2. Reproducibility: How to reproduce the issue (e.g. package version, system OS, code snippets, screenshots). A good issue provides helpful clues. However, if the issue is a simple task, a meta-issue, a discussion, or otherwise straightforward, reproduction steps are not strictly required. This is mainly important for bug reports.
3. PR and Triage Status: Is there any PR open while the issue still needs triage? Look for tags like `needs-triage` or PR links. If it's pending triage but has a PR, it may need more context.
4. Context & Details: The description should provide enough overall context to be actionable for a maintainer.

Decision rules for Issues:
- Pass if: The issue's purpose is understandable, provides sufficient helpful clues for its type (e.g. tracking tasks vs. bug reports), and a maintainer would have enough context to take action.
- Needs Details if: The issue is a standard bug/feature report with vague descriptions, no helpful clues, or lacks the necessary context to be actionable for a maintainer.
=== END CRITERIA ===

1. Evaluate the submission's title and description (body) against the above criteria.
