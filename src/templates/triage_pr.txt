=== EVALUATION CRITERIA ===
For Pull Requests, evaluate the content by looking at the following aspects. Be reasonable. Flag a PR if it is obviously missing crucial context. Self-evident changes do not need exhaustive explanations or testing documentation.
1. Title Context: The PR title should provide a reasonable summary of what the change does.
2. Body Description: The PR body should concisely explain why the change is needed and what it does. Complex changes should explain the approach, but for straightforward changes or utility scripts, a simple summary is sufficient. Do not penalize for boilerplate text if the core message is clear.
3. Code Diff Consistency: If code changes (diffs) are provided, verify that the PR description roughly aligns with the changes being made. A submission should only be flagged if the code changes are completely unrelated to what the description claims.
4. Testing Context: It is helpful if the PR mentions how it was tested. However, if the change is straightforward or test coverage is obvious from the code, exhaustive testing context is not required.
5. Code Signal: Analyze the code changes to flag truly low-signal contributions. Purely stylistic edits or simple word renames need an explanation. However, functional improvements, tests, or utility scripts (even if short) provide value and should not be penalized as low-signal.

Decision rules for Pull Requests:
- Pass if: The PR's purpose is understandable, reasonably aligns with the code changes, and a reviewer would have enough context.
- Needs Details if: The PR is an empty code dump with absolutely no explanation, the rationale for a complex change is entirely unclear, the description contradicts the actual code changes, or the PR consists solely of trivial renames/stylistic edits without any rationale.
=== END CRITERIA ===

Instructions:
1. Evaluate the submission's title and description (body) against the above criteria.
2. Verify if the Pull Request links to an existing issue. If it links to an issue that has the 'needs-triage' label, you should mark it as Needs Details because maintainers must review the issue first.
3. Determine if the submission passes the criteria.
4. Output your evaluation strictly as a JSON object with the following two keys:
   - "result": The exact string "Pass" or "Needs Details".
   - "reason": A short 1-3 sentence explanation for your result.
