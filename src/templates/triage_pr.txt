evaluate whether a new {event_type} submission provides sufficient context for contributors to analyze and reproduce, and whether it follows the project's contribution guidelines.

=== EVALUATION CRITERIA ===
For Pull Requests, evaluate the content by looking at the following aspects. Be reasonable—small, trivial changes do not need exhaustive explanations or testing documentation.
1. Title Context: The PR title should provide a reasonable summary of what the change does. Indicating the exact type of change (e.g., "Fix") is helpful but not strictly required if the title is otherwise descriptive.
2. Body Description: The PR body should concisely explain why the change is needed and what it does. Complex changes should explain the approach or trade-offs, but for straightforward fixes, a simple summary is sufficient.
3. Code Diff Consistency: If code changes (diffs) are provided, verify that the PR description accurately reflects the changes being made in the code. A submission is of low quality if the code changes are not related to what the description claims.
4. Testing Context: It is helpful if the PR mentions how it was tested. However, if the change is trivial or test coverage is obvious from the code, exhaustive testing context is not strictly required.

Decision rules for Pull Requests:
- Pass if: The PR's purpose is understandable, aligns with the code changes (if provided), and a reviewer would have enough context to review it.
- Needs Details if: The PR is a code dump with no explanation, the rationale for the change is entirely unclear, or the description is unrelated to the actual code changes.
=== END CRITERIA ===
